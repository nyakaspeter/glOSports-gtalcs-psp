# lcs-recomp port review, 2026-10-28

Scope: bugs and slow-downs in the psprecomp runtime, the code generator, the GE
executor and the GLES2 backend, as built by `build.sh` (patch 0015, PGO, GCC 12,
`-O2` for the generated units). Evidence is from the ARM disassembly of the
current build (`build/lcs/CMakeFiles/.../generated_unit_0100.cpp.o`), from small
probe translation units compiled with the project's exact flags
(`build/probe/`), from static counts over the 215 generated units, and from the
safehouse benchmark with `psample` (section 3).

Safehouse baseline for this review: see section 3.

## 1. Confirmed bugs

### B1. Branch-and-link writes `$ra` before the branch condition reads it
`tools/codegen_main.cpp:1020`. For `bltzal`/`bgezal`/`bltzall`/`bgezall` the
generator emits `ctx.set_gpr(31, pc+8)` and only then evaluates
`branch_condition(decoded)`. If `rs` is `$ra` the condition sees the new link
value. Compilers never emit `bltzal $ra`, so no effect on LCS; it is a one-line
reorder. Generic. Risk: none.

### B2. `prescan_ge_list` races the GE thread on `ge_base_register` / `ge_offset_address`
`lcs/host/lcs_ge_exec.cpp:148-149` reads the executor's file-scope BASE and
OFFSET registers, which `execute_ge_list_rendered` (GE worker thread) writes
while running a list. `lcs_profile.cpp:3284` calls the prescan on the game
thread from the VBlank-interrupt path without `ge_worker_wait_idle()`. A torn
read mis-resolves a JUMP/CALL in the scanned list, so FINISH is missed and the
GE finish callback is not queued for that list. Rare (the vblank list is short)
but real. Fix: copy BASE/OFFSET under the worker mutex, or seed the prescan from
the list's own state only. LCS-specific file, but the pattern (shared executor
globals) is generic. Risk: low.

### B3. The plain direct-chain form never sets `ctx.pc` (latent)
`tools/codegen_main.cpp:853-890` (`emit_target`) emits
`invoke_chained_direct<&recomp_unit_N, N>(ctx, &aot_mem)` with no entry id and
no `ctx.pc = target` store when a fixed target has no entry id in its unit;
the callee then dispatches on whatever `ctx.pc` last held. In this corpus the
form occurs at exactly four sites, all in `generated_unit_0212.cpp` in blocks
that are mis-decoded data (`"unknown not lowered yet"` precedes them), so it
never runs. Worth an assert in the generator rather than a fix. Generic.

## 2. Speed-ups, ranked

Each entry: what, where, evidence, expected gain, scope, risk. "Host
instructions" are from the probes compiled with the project flags
(`build/probe/probe.cpp`, `probe2.cpp`).

### S1. Guest memory: map guest RAM and VRAM into one reserved 512 MB window (fastmem)
Where: `include/psprecomp/guest_memory.hpp:67-125` (AotFastView), `src/guest_memory.cpp:72`,
codegen `tools/codegen_main.cpp:179-197,1294`.

Evidence. A guest `lw` today compiles to 10 host instructions and a conditional
branch: load base register from `ctx`, add immediate, `bic` + `add` to
canonicalise and rebase, reload `ram_limit32_` from the view, compare, branch,
reload `ram_data_` from the view, the load itself, store to `ctx`. The probe
with five memory ops plus one add is 62 instructions (50 on the hot path);
the same guest code against a reserved 512 MB window with no range check is
25 instructions, branch-free, and needs no out-of-line slow path
(`probe_mem` vs `probe_mem_fastmem`). Unit 0100 alone has 1,188 memory sites
and 1,166 `bl` sites to the `*_slow` helpers; the corpus has 283,213 guest
memory ops in 718,020 instructions (39%). Keeping the view's fields in
address-free locals instead was also probed (`probe_mem_locals`, 61
instructions): no gain, the reloads are forced by the byte-typed guest store
that may alias everything, not by the reference.

Additional LCS effect: display lists are built in VRAM with CPU stores, and
every VRAM access today leaves the inline path for `aot_store32_slow`
(`guest_memory.cpp:151`, a `resolve()` per access). With VRAM mapped at
`+0x04000000` (four 2 MB mirrors of one `memfd`) those become the same
2-instruction path.

Expected gain: memory ops are 39% of guest instructions and about half of the
host instructions in a typical block; halving their cost is an estimated
15-25% of the game thread (37 ms), plus roughly 3 MB less code. Generic to
psprecomp. Risk: medium. Needs a SIGSEGV handler to report stray guest
accesses (scratchpad at 0x00010000 and the hardware register window can be
mapped or left faulting), `raw_pointer`/`bytes()` callers updated, and the
AOT units rebuilt (profile retrain, ~1.5 h). About two days. Not started.

### S2. VFPU prefixes: fold them at codegen time
Where: `tools/codegen_main.cpp:318` (Vpfx), `:577` (VfpuVec3) and every
`execute_vfpu_*_ct` / `read_vfpu_vector_with_source_prefix_ct` /
`write_vfpu_vector_with_destination_prefix_ct` site;
`include/psprecomp/allegrex_context.hpp:212,277,628,1410`.

Evidence. The whole game contains 52 `vpfx` instructions (grep over the
generated units), every one consumed by the next VFPU op in the same basic
block (awk check, 0 dangling). Yet 3,563 + 2,192 source-prefix reads, 4,418
destination-prefix writes, and every `vdot`/`vscl`/`vcmp`/`vcmov`/`compare3`
site decode the prefix registers at run time: a 3-lane `vsub` with prefixes is
269 host instructions (`probe_vfpu_prefixed`), the same op without them is
14 (`probe_vfpu_plain`); `vscl.t` is 225, `vdot.t` 231. With default
prefixes the executed part is still ~26 extra instructions per op (two
`ldr`+`cmp`+branch on the reads, per-lane saturation and write-mask tests on
the write, three stores in `eat_vfpu_prefixes`), and the cold part bloats the
units (roughly 10 MB of the 48 MB of generated text).

Change: a per-block prefix tracker in `emit_function_source`. At block entry
the prefixes are the defaults (every consumer resets them today, and no
`vpfx` crosses a block). A `vpfx` records its literal; the consuming op is
emitted with a compile-time prefix (a template parameter, swizzle/abs/neg/
constant resolved statically) and no `eat_vfpu_prefixes`; every other op is
emitted with the plain `_ct` accessors. The `ctx.vfpu_ctrl` stores stay only
for `mtv`/`mfv` of control registers. VFPU ops are 20% of the static corpus;
the dynamic share is in the profile below.

Expected gain: 3-10% of the game thread, more code locality. Generic. Risk:
low (the invariant is checked mechanically at generation time: abort if a
prefix is pending at a block end). One day.

### S3. `mul.s`: drop the `inf*0` special case on ARM hosts
Where: `tools/codegen_main.cpp:254`.
Evidence: today 29 host instructions with four `vcmp`/`vmrs` pairs; a plain
`vmul.f32` is 6 (`probe_muls` vs `probe_muls_plain`). The check exists because
x86 produces a negative default NaN; ARM VFP produces 0x7FC00000 for
`inf*0` by itself (default NaN, sign 0), which is exactly the value the check
forces. Expected gain: small per op but `mul.s` is common in physics; ~1% of
the game thread. Generic for ARM hosts (`#if defined(__arm__)` in the emitted
code). Risk: none on ARM.

### S4. Cross-unit call bookkeeping: 64-bit counters and a GOT load per call
Where: `include/psprecomp/runtime.hpp:230-237,317` (`dispatches_since_import_`,
`g_runtime_starvation_interval_fast` are `uint64_t`), `build.sh` (the binary
is PIE).
Evidence (unit 0100 disassembly around every `bl recomp_unit_*_entry`): after
each call, `ldrb` of `chain_context_invalidated_`, a GOT-relative load of the
interval (`ldr r3,[pc]; ldr r3,[fp,r3]; ldrd`), a 64-bit increment
(`ldr/ldr/adds/adc/str/str`), a 64-bit compare, and the depth decrement: about
22 instructions after and 14 before the call, on 341 call sites in this unit
alone. `fp` is reserved as the GOT base for the whole 200 KB function because
the executable is PIE (`file build/lcs/LCSNative`: "pie executable"), one
register fewer for the register-starved generated code.
Change: a 32-bit countdown (`if (--budget == 0) boundary()`), and
`-fno-pie -no-pie` in `build.sh` (the PGO profile stays valid; code layout
does not change).
Expected gain: 1-3% of the game thread. Generic. Risk: none. Half a day
including the A/B.

### S5. GE: the per-draw fixed cost in `render_ge_primitive`
Where: `lcs/host/ge_renderer.cpp:4155-4910`, `lcs/host/ge_gpu_backend_gles2.cpp`.
Evidence (static): every draw that reaches the backend builds
`GeGpuDrawDescriptor` (352 bytes) from ~80 command registers (`:4203-4290`),
copies it three times (`effective_draw`, `batch.draw`, `job`), builds the
`GeGpuHardwareTransform` (192 bytes, two 4x4 products) twice (`:4185` for the
cull and `:4580` again), recomputes `texture_key` (25 hash mixes) up to five
times, runs `prepare_lighting` (four lights, ~60 float24 decodes) every draw
because the executor passes no revision, and takes the backend's recursive
mutex 6-8 times (`ge_gpu_backend_gles2.cpp`, 20 lock sites). Per frame that is
about 1.5 KB of descriptor writes per draw, 3.7 MB for 2,450 draws, read back
by the render thread.
Change (generic ge_renderer): one `GeGpuHardwareTransform` per draw; a dirty
mask kept by the list executor (`lcs_ge_exec.cpp:84`, one table lookup per
list word) so the descriptor's texture/blend/lighting groups are rebuilt only
when a register in the group changed (the full-state revision tried earlier
missed because *some* register always changes); the mutex taken once per
draw, or not at all on the GE thread's own state. A slim `Batch` (index,
count, pointer to a shared state record) instead of a 550-byte copy.
Expected gain: from the profile (section 3.1), 25-35% of the GE thread is this
kind of per-draw overhead; 10-15% of it is reachable in two days. Risk:
low-medium (touches ge_renderer, so retrain).

### S6. Render thread: static geometry resident on the GPU
Where: `ge_gpu_backend_gles2.cpp:1505-1525` (one `glBufferData` of the frame's
vertices per frame), `:2340-2380` (`s.packed.insert` per draw).
Evidence: ~800 KB of packed vertices are memcpy'd on the GE thread and
re-uploaded by the driver every frame although the world geometry does not
change between frames. Cheap, exact change detection is the problem: guest
stores are untracked. Two options: (a) with S1 in place, keep resident
meshes' pages read-only and catch the first write (the PPSSPP/Dolphin
scheme; zero cost on the hot path, a fault only when streaming loads a new
model); (b) a per-64 KB generation counter bumped by every guest store (+3
host instructions per store, ~2% of the game thread). The render thread's
share for the upload and its index copies is in the profile.
Expected gain: only pays once the GE and game threads are faster (the render
thread is 35 ms, the other two 37-40 ms). Generic. Risk: medium. Three days.
Depends on S1 for option (a).

### S7. Small, LCS-specific
- `lcs_profile.cpp:1148-1170` `promote_expired_delays` allocates and frees a
  `std::vector` on every starvation tick (every 256 chained calls) and on every
  scheduler switch; make it `thread_local`. ~0.5% of the game thread.
- `lcs_profile.cpp:1121` `best_ready_thread` does two hash-map lookups per
  comparison; cache the priority in the continuation. Same order.
- `lcs/CMakeLists.txt:151` compiles the generated units `-O2` while the rest
  is `-O3`; probably intentional for build time, worth one A/B.

## 3. Measurements (safehouse benchmark)

`build/` was stale at the start of the review: it still contained the
reverted cull-ahead experiment (the sources were reverted after the last
build and `ninja` did not notice), so `out/lcs/LCSNative` differed from the
installed binary and a first profile of it showed a 29% `CullAhead::run`
thread and lock contention that do not exist in the real build. The host
sources were touched, rebuilt (`nm | grep CullAhead` empty, md5 380d9347,
BuildID c250b464) and deployed as `ports/lcs/LCSNative.test`; everything below
is from that binary. The symbolised profiles are in
`profiles/2026-10-28-safehouse/`, the tool in `tools/psample-symbolise.py`.
`psample` samples wall-clock state, so a thread blocked in a syscall is
counted; the "blocked" rows are that.

| | LCSNative.test (= patch 0015) |
|---|---|
| fps, 10 s with no sampler | 24.9 |
| fps with the sampler attached (250 Hz on 3 threads) | ~21 |
| PSP draws / GL draws per frame | 1323 / 926 |
| KB per frame: float vertices / packed / indices / textures | 219 / 621 / 158 / 0 |
| thread CPU: game / render / GE | 90 / 90 / 98 % |
| other threads | Mali notification thread 11%, SDL audio 12% |

Symbol tables: `nm` of `build/lcs/LCSNative`, the console's `/lib/libc.so.6`
and `/usr/local/lib/mali/lib/libMali.so`. libc is stripped, so its internals
are named by the nearest exported symbol; the hot ones were checked by
disassembly: `libc+0x6ad80` and `+0x23d00` are `svc 0` syscall stubs (futex
waits and `ioctl`), `+0x790c0`/`+0x78d00` the NEON `memcpy` body,

### 3.1 What the profile changes in the ranking
- The GE thread is the limiter at this scene: 98% busy, and the game thread
  waits for it 13% of the time. S5 (per-draw cost) moves to the top; the
  codegen work (S1-S4) is still needed because the game thread must also
  drop below 33 ms, but alone it would only grow the wait share.
- For the GE thread, in order of size: (a) the float-vertex path, 16%,
  decodes and lights every vertex of Toni and the vehicles every frame
  (`decode_model_vertex_for_gpu` per vertex; `StaticVertexCache` exists but
  re-hashes the raw bytes of every draw to validate, `ge_renderer.cpp:1680`);
  (b) `memset` + the `render_ge_primitive` share of `memcpy`, ~13%, is the
  per-draw zeroing and copying of the 352-byte descriptor, 644-byte transform
  state, 1 KB command array and the job (`:4203`, `:4640-4670`); (c) the
  cull, 10%, scans every packed vertex (int16 min/max, scalar) and then
  builds the full transform (4.3%, half of it only for the cull); a
  NEON min/max over the 10-byte stride and one transform per draw are
  direct; (d) the mutex, ~7%, by not locking on the GE thread's own path;
  (e) list parsing, 7%: `update_ge_transform_state` and the switch per word;
  (f) texture bookkeeping, ~5%.
- The packed vertex copy (`s.packed.insert`, 621 KB/frame, 8.6% of the thread
  as memcpy) only goes away with resident geometry (S6).
- The game thread's own slow paths (VRAM list writes, `lwl`/`lwr`, out-of-line
  VFPU helpers) are 3% and are removed by S1 and S2.

## 4. Dead ends checked here (no change needed)
- Keeping the AotFastView fields in locals: no gain (probe, 61 vs 62
  instructions); the reload is due to byte-store aliasing, not the reference.
- `__restrict` on the generated signatures (already in the README): same
  reason.

## 5. Outcome (same day)

Kept, each as a patch, each a win in alternating runs against the installed
patch-0015 build (the reference, 23-25 fps in the safehouse bench):

| patch | change | A/B (test vs reference) |
|---|---|---|
| 0016 | per-file PGO retrain (10 min instead of 1.5 h) | tooling |
| 0017 | transform once per draw, no backend mutex, no per-draw copies/zeroing | 26.3 / 26.0 vs 25.2 / 23.1 |
| 0018 | NEON cull scan, target size cached | 25.8 / 26.7 vs 24.0 / 25.0 |
| 0019 | table-driven list loop, lighting/transform revisions, texture-matrix fix, texture recheck every 4th frame | 26.2 / 26.6 vs 24.7 / 24.0 |
| 0020, 0021, non-PIE | VFPU prefix fold, ARM `mul.s`, 32-bit chain countdown | 26.7 / 27.1 vs 24.6 / 23.6 |
| 0022 | fastmem with page generations | 27.5 / 26.5 vs 23.8 / 23.7 |

Final build (LCSNative.test on the console): 27.4 fps; game thread 79%, GE
87%, render thread 100%. The render thread is the limiter and about half of
it is inside ARM's driver and its kernel calls. Four render-thread attempts
(index-loop/clip-row cache, pipeline depth 2, malloc tunables, GE-side writes
into a mapped GPU buffer) all measured as noise and were not kept; the
details are in the README's dead-end list.

Not done from the plan: S6 resident geometry. With merging, vertices of one
GL draw must share a buffer at 10-byte-aligned offsets, which consecutive
meshes in guest memory do not satisfy, so it would cost ~40% more GL draws;
the driver's per-draw cost makes that a likely loss. The page generations
from 0022 are in place if a different design wants them (cached bounding
boxes on the GE thread, for one).
